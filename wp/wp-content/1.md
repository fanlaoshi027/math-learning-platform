## 1. 项目定位

这是一个面向初中/高中数学培训课程的在线课程网站。

核心使用场景：

1. 老师上传、管理数学课程。

2. 课程主要包括：

● “大培优”配套课程；

● 专题课程。

3. “大培优”类课程以教材/资料页码作为主要课时定位方式。

4. 学员登录后根据授权观看课程。

5. 游客可以观看指定的免费试看章节/课时；需要解锁的内容要求登录并验证权限。

6. 视频在电脑端提前切片为 HLS（M3U8），上传到阿里云服务器。

7. 视频需要防盗链、Token 鉴权、尽量降低直接下载/猜地址的可能。

8. 视频可以使用 AES 加密；需要权衡服务器负载、CDN/网络开销和播放体验。

9. 播放器支持动态水印，后台可设置：

● 水印位置；

● 透明度；

● 大小；

● 后续可考虑移动/随机位置。

10. 后台可设置多设备策略。

11. 学员授权按课程控制。

12. 编辑/新增学员时，可以设置该学员对哪些课程有权限。

13. 编辑课程时，可以查看/管理哪些学员被授权。

14. 前台需要有漂亮、现代、适合数学教育产品的 UI。

15. 后台要尽量简单，不希望日常课程管理必须进入 Tutor LMS 原生复杂后台。

16. 但 Tutor LMS 原生后台必须保留，作为高级/备用维护入口。

## WordPress / Tutor LMS 开发规范

这是最高优先级原则。

3.1 不修改 WordPress 核心

禁止：

```text  
wp-admin/  
wp-includes/  
```

等核心文件。

使用：

● Hooks

● Filters

● WordPress APIs

● REST API

● Settings API

● Options API

● Users / Roles / Capabilities

● WP Filesystem

● WP-Cron（如适合）

● $wpdb + prepared statements（必要时）

  

3.2 不修改 Tutor LMS 插件源码

禁止直接修改：

```text

```

● Hooks

● Filters

● Models / Service（以 4.0.4 实际源码为准）

● 官方 API

● WordPress 数据接口

进行扩展。

  

3.3 Tutor LMS 4.0.4 是当前开发基准

所有 Tutor LMS 对接代码：

> 必须核对 Tutor LMS 4.0.4 实际源码和官方开发文档。

尤其是：

● Course 创建；

● Topic 创建；

● Lesson 创建；

● Topic/Lesson 排序；

● Course Builder；

● Lesson Preview；

● Enrollment；

● Access；

● REST API；

● Hook；

● Custom Field。

不能凭记忆写一个看起来合理的 Tutor 函数名。

  

## 为什么要有 Tutor Adapter

MathCourse 不应该在几十个地方直接调用 Tutor LMS。

建立：

```text  
MathCourse  
└── Tutor  
    └── Adapter  
```

业务代码只调用自己的业务层。

逻辑关系：

```text  
前台/后台  
    ↓  
MathCourse Service  
    ↓  
Tutor Adapter  
    ↓  
Tutor LMS 4.0.4  
```

例如逻辑接口可以有：

```text  
get_course()  
get_courses()  
create_course()  
update_course()  
  
get_topics()  
create_topic()  
  
get_lessons()  
create_lesson()  
update_lesson()  
delete_lesson()  
```

注意：上述是业务接口设计，不代表 Tutor LMS 4.0.4 一定存在同名函数。

Adapter 内部负责把业务需求转换成 Tutor LMS 4.0.4 实际 API / Model / Hook。

以后 Tutor LMS 升级时，重点维护 Adapter。

## 页码设计

“大培优”最重要的业务特点就是页码。

一个 Lesson 仍然是：

> **Tutor LMS 原生 Lesson**

而不是自己重新发明一种 Lesson。

额外增加业务字段，例如：

```text  
page_number  
is_trial  
video_id  
```

示例：

```text  
Lesson ID = 583  
title = 第86页  
page_number = 86  
is_trial = true  
video_id = xxx  
```

  

## 页码字段职责

标题：

```text  
第86页  
```

用于人类阅读。

page_number：

```text  
86  
```

用于程序查询。

例如用户输入：

```text  
86  
```

系统直接按 page_number=86 定位，而不是模糊搜索标题。

  

## 专题课程不需要页码

专题课程：

```text  
page_number = null  
```

只有：

```text  
course_type = supplementary  
```

的大培优配套课程使用页码。

## 批量创建不能一次性卡死浏览器

不能简单：

```text

```

应该使用批处理任务：

```text

↓  
分批执行  
↓

```

```text

已完成：286  
失败：0  
  
正在创建第287页……  
```

以后视频扫描同样复用这个思想。

  

## 批量任务的失败恢复

如果创建到第237页服务器出错：

不能留下不可控半成品。

应该记录：

```text  
任务ID  
course_id  
topic_id  
current_index  
total  
status  
error  
```

支持：

```text  
继续  
重试  
取消  
```

注意：

> WordPress/Tutor 的多个操作不一定能简单使用传统数据库事务，因此采用“可恢复批处理”比声称全部事务回滚更现实。

## 视频系统总体方案

电脑端提前处理：

```text  
原始视频  
↓  
FFmpeg  
↓  
HLS  
↓  
M3U8 + TS/fMP4 分片  
↓  
AES 加密（计划采用）  
↓  
上传服务器  
```

一个课时一个目录，例如：

```text  
课程/随机ID/  
    index.m3u8  
    key.key  
    000.ts  
    001.ts  
    ...  
```

但最终实际目录/文件名：

> **不能使用简单的“086/index.m3u8”这种可猜地址结构。**

  

## 试听课的视频地址必须与正式课不同

这是已经明确的产品安全要求。

不能：

```text  
试看：  
/video/086/index.m3u8  
  
正式：  
/video/086/index.m3u8  
```

否则游客拿到地址后可能猜到正式资源。

目标：

```text  
试看资源  
独立随机 storage key  
  
正式资源  
另一个独立随机 storage key  
```

例如：

```text  
trial/<高熵随机ID>/  
course/<高熵随机ID>/  
```

实际路径不能根据页码直接推导。

  

## 视频数据库不要保存固定公开 URL

优先保存：

```text  
storage_key  
```

例如：

```text  
a8F3xK9p/Q2m7/  
```

播放时：

```text  
用户  
 ↓  
课程授权检查  
 ↓  
Lesson权限检查  
 ↓  
生成短期Token  
 ↓  
生成临时播放地址  
 ↓  
Nginx鉴权  
 ↓  
HLS  
```

  

## 防盗链

目标：

```text  
合法用户  
 ↓  
短期 Token  
 ↓  
Nginx  
 ↓  
允许  
```

直接复制：

```text  
m3u8 URL  
```

到其他地方：

> Token 过期/来源不合法 → 拒绝。

同时考虑：

● Referer；

● Origin；

● IP/会话绑定（需谨慎，避免移动网络导致误伤）；

● Token TTL；

● key 请求鉴权；

● 分片请求鉴权。

不要仅依赖 Referer。

  

## 防下载的正确认识

必须明确：

> **浏览器能够播放的视频，从技术上不能做到绝对“不可下载”。**

我们能做的是显著提高获取原始资源的成本：

```text  
HLS  
+  
AES  
+  
短期 Token  
+  
Nginx 鉴权  
+  
独立随机路径  
+  
Key 鉴权  
+  
动态水印  
+  
设备限制  
```

目标是：

> 防止普通用户直接复制地址、猜路径、简单下载。

而不是宣称 100% 防录屏/防下载。

  

## AES 加密

计划采用：

> HLS AES-128。

典型：

```text  
index.m3u8  
↓  
key URI  
↓  
AES key  
↓  
encrypted segments  
```

电脑端切片/加密。

需要考虑：

● 加密不会消除网络传输；

● 播放时仍需要解密；

● Key 请求也必须保护；

● AES-128 对服务器负载的影响通常不是主要瓶颈，真正需要关注的是并发、带宽、I/O、鉴权请求等；

● 最终以实际服务器测试为准。

  

## 阿里云服务器

目前计划：

> 阿里云轻量应用服务器。

已讨论：

> 峰值带宽 200 Mbps。

初期演示/小规模使用可以先按这个配置设计。

但正式上线前必须根据：

```text

同时在线人数  
并发播放数  
HLS请求数量  
峰值流量  
```

做容量测试。

不能只根据“200 Mbps”一个参数保证人数。
