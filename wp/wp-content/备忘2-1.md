## 1. 项目定位

这是一个面向初中/高中数学培训课程的在线课程网站。

核心使用场景：

1. 老师上传、管理数学课程。

2. 课程主要包括：

● “大培优”配套课程；

● 专题课程。

3. “大培优”类课程以教材/资料页码作为主要课时定位方式。

4. 学员登录后根据授权观看课程。

5. 游客可以观看指定的免费试看章节/课时；需要解锁的内容要求登录并验证权限。

6. 视频在电脑端提前切片为 HLS（M3U8），上传到阿里云服务器。

7. 视频需要防盗链、Token 鉴权、尽量降低直接下载/猜地址的可能。

8. 视频可以使用 AES 加密；需要权衡服务器负载、CDN/网络开销和播放体验。

9. 播放器支持动态水印，后台可设置：

● 水印位置；

● 透明度；

● 大小；

● 后续可考虑移动/随机位置。

10. 后台可设置多设备策略。

11. 学员授权按课程控制。

12. 编辑/新增学员时，可以设置该学员对哪些课程有权限。

13. 编辑课程时，可以查看/管理哪些学员被授权。

14. 前台需要有漂亮、现代、适合数学教育产品的 UI。

15. 后台要尽量简单，不希望日常课程管理必须进入 Tutor LMS 原生复杂后台。

16. 但 Tutor LMS 原生后台必须保留，作为高级/备用维护入口。

## WordPress / Tutor LMS 开发规范

这是最高优先级原则。

3.1 不修改 WordPress 核心

禁止：

```text  
wp-admin/  
wp-includes/  
```

等核心文件。

使用：

● Hooks

● Filters

● WordPress APIs

● REST API

● Settings API

● Options API

● Users / Roles / Capabilities

● WP Filesystem

● WP-Cron（如适合）

● $wpdb + prepared statements（必要时）

  

3.2 不修改 Tutor LMS 插件源码

禁止直接修改：

```text  
wp-content/plugins/tutor/  
```

● Hooks

● Filters

● Models / Service（以 4.0.4 实际源码为准）

● 官方 API

● WordPress 数据接口

进行扩展。

  

3.3 Tutor LMS 4.0.4 是当前开发基准

所有 Tutor LMS 对接代码：

> 必须核对 Tutor LMS 4.0.4 实际源码和官方开发文档。

尤其是：

● Course 创建；

● Topic 创建；

● Lesson 创建；

● Topic/Lesson 排序；

● Course Builder；

● Lesson Preview；

## 为什么要有 Tutor Adapter

MathCourse 不应该在几十个地方直接调用 Tutor LMS。

建立：

```text  
MathCourse  
└── Tutor  
    └── Adapter  
```

业务代码只调用自己的业务层。

逻辑关系：

```text  
前台/后台  
    ↓  
MathCourse Service  
    ↓  
Tutor Adapter  
    ↓  
Tutor LMS 4.0.4  
```

例如逻辑接口可以有：

```text  
get_course()  
get_courses()  
create_course()  
update_course()  
  
get_topics()  
create_topic()  
  
get_lessons()  
create_lesson()  
update_lesson()  
delete_lesson()  
```

注意：上述是业务接口设计，不代表 Tutor LMS 4.0.4 一定存在同名函数。

Adapter 内部负责把业务需求转换成 Tutor LMS 4.0.4 实际 API / Model / Hook。

以后 Tutor LMS 升级时，重点维护 Adapter。

## 页码设计

“大培优”最重要的业务特点就是页码。

一个 Lesson 仍然是：

> **Tutor LMS 原生 Lesson**

而不是自己重新发明一种 Lesson。

额外增加业务字段，例如：

```text  
page_number  
is_trial  
video_id  
```

示例：

```text  
Lesson ID = 583  
title = 第86页  
page_number = 86  
is_trial = true  
video_id = xxx  
```

  

## 页码字段职责

标题：

```text  
第86页  
```

用于人类阅读。

page_number：

```text  
86  
```

用于程序查询。

例如用户输入：

```text  
86  
```

系统直接按 page_number=86 定位，而不是模糊搜索标题。

```text

```

只有：


## 批量任务的失败恢复

如果创建到第237页服务器出错：

不能留下不可控半成品。

应该记录：

```text  
任务ID  
course_id  
topic_id  
current_index  
total  
status  
error  
```

支持：

```text  
继续  
重试  
取消  
```

注意：

> WordPress/Tutor 的多个操作不一定能简单使用传统数据库事务，因此采用“可恢复批处理”比声称全部事务回滚更现实。

## 视频系统总体方案

```text

↓

↓

↓

```

一个课时一个目录，例如：

```text

    index.m3u8  
    key.key  
    000.ts  
    001.ts  
    ...
```

但最终实际目录/文件名：

> **不能使用简单的“086/index.m3u8”这种可猜地址结构。**

  

## 试听课的视频地址必须与正式课不同

这是已经明确的产品安全要求。

不能：

```text

```

目标：

```text

```

例如：

```text

```

实际路径不能根据页码直接推导。

## 防盗链

目标：

```text  
合法用户  
 ↓  
短期 Token  
 ↓  
Nginx  
 ↓  
允许  
```

直接复制：

```text

```

到其他地方：

同时考虑：

● Referer；

● Origin；

● IP/会话绑定（需谨慎，避免移动网络导致误伤）；

● Token TTL；

● key 请求鉴权；

● 分片请求鉴权。

不要仅依赖 Referer。

  

## 防下载的正确认识

必须明确：

> **浏览器能够播放的视频，从技术上不能做到绝对“不可下载”。**

我们能做的是显著提高获取原始资源的成本：

```text  
HLS  
+  
AES  
+  
短期 Token  
+  
Nginx 鉴权  
+  
独立随机路径  
+  
Key 鉴权  
+  
动态水印  
+  
设备限制  
```

目标是：

> 防止普通用户直接复制地址、猜路径、简单下载。

而不是宣称 100% 防录屏/防下载。

  

## AES 加密

计划采用：

> HLS AES-128。

典型：

```text  
index.m3u8  
↓  
key URI  
↓  
AES key  
↓  
encrypted segments  
```

电脑端切片/加密。

需要考虑：

● 加密不会消除网络传输；

● 播放时仍需要解密；

● Key 请求也必须保护；

● AES-128 对服务器负载的影响通常不是主要瓶颈，真正需要关注的是并发、带宽、I/O、鉴权请求等；

● 最终以实际服务器测试为准。

# 2. 200Mbps 到底够不够？

200Mbps 理论峰值大约：

**25MB/s**

假设一条 1080p 视频平均：

```
4 Mbps
```

一个用户大约：

```
0.5 MB/s
```

理论上：

```
25 ÷ 0.5 ≈ 50 人
```

但这只是数学上的理论值。

实际还要考虑：

- 网络波动
- HTTP 请求
- HLS 分片
- WordPress 访问
- 图片
- 后台操作
- 其他网络开销

所以我们不要按 50 个并发去设计。

我会把第一阶段的**比较舒服的目标**放在：

> **十几到二三十个同时播放用户**

对于刚开始运营的个人数学课程网站，已经相当够用了。

------

# 3. 视频编码不要追求过高码率

你录课主要是：

> CAD / 几何图形 / 数学讲解 / 屏幕录制

这种内容其实不需要电影级码率。

建议：

### 1080p

```
H.264
30fps
平均 3～5 Mbps
```

如果文字、CAD线条比较多，可以适当提高到：

```
5～6 Mbps
```

这样既保证：

- 数学公式清楚
- CAD线条清楚
- 文件不会过分巨大

又不会把服务器带宽浪费掉。

管理和传输都比较现代。

# 6. Nginx 负责真正的视频访问控制

这一层很重要。

我们最终不是：

```
浏览器
 ↓
直接访问 /video/xxx/index.m3u8
```

而是：

```
浏览器
 ↓
WordPress
 ↓
授权验证
 ↓
签名播放地址
 ↓
Nginx
 ↓
视频文件
```

Nginx 可以负责：

- 防盗链
- Token 验证
- 过期时间
- 禁止目录浏览
- 禁止直接访问
- 限制请求来源

这样 WordPress 不需要自己承担所有视频流量。

------

# 7. WordPress 不应该代理整个视频

这个一定要避免。

错误方案：

```
用户
 ↓
WordPress PHP
 ↓
读取视频
 ↓
再传给用户
```

这样 PHP 和服务器 CPU 很容易被拖死。

正确：

```
用户
 ↓
WordPress PHP
 ↓
只负责鉴权
 ↓
Nginx
 ↓
直接发送视频
```

WordPress 只负责：

> **“你有没有资格看？”**

Nginx负责：

> **“视频怎么传给你？”**

# 十四、现在还有几个真正值得讨论的问题

目前**课程、学员、授权、Lesson、页码、视频、试看、HLS、防盗链、后台界面**这些大的架构，我认为已经可以定了。

剩下我认为有 **5 个问题值得我们继续讨论**：

### ① 视频服务器到底放在哪里

现在：

> 阿里云轻量服务器本地存储

以后：

> OSS / CDN

需要确定第一版具体怎么落地。

---

### ② 视频上传方式

你目前说的是：

> 电脑切片 → 上传服务器。

这里需要决定：

**A. 浏览器后台上传**

还是：

**B. 用专门的上传工具/FTP/SFTP**

还是：

**C. 电脑端一个文件夹，自动同步到服务器。**

对于你这种一次可能上传几百个课时的情况，我比较倾向 **C**。

---

### ③ HLS 加密程度

目前我们已经确定：

> 随机目录 + Token + M3U8/分片鉴权。

还需要决定是否进一步使用：

> **HLS AES-128 加密**

这个会进一步提高直接抓取分片的难度，但也会增加处理复杂度。

---

### ④ 是否需要给视频加动态水印

例如播放时显示：

```text
张三
138****8888
```

甚至：

```text
张三 · 数学课堂
```

如果有人录屏传播，可以追溯来源。

这个属于**防录屏/追责层**，不是防下载本身。

---

### ⑤ 最后才是手机端体验

电脑端目前已经比较清楚。

但你这个网站以后很可能大量通过：

* 微信
* 手机浏览器
* iPhone
* 安卓手机

访问。

所以最后还需要专门确定：

> **手机端学习中心 + 播放器 + 大培优页码定位到底怎么做。**

---

**我建议下一步先讨论第②项“视频上传方式”。**

# ④ 不要让你自己管理随机 ID

## 接下来还有两个技术问题值得讨论

### A. HLS 要不要 AES-128 加密

它主要解决：

> 即使有人拿到了 HLS 分片，也不能直接播放。

### B. 要不要做动态水印

例如播放时显示：

> `张三 · 数学课堂`

它主要解决：

> **防录屏传播和追踪泄露来源。**

我建议**先讨论 A，再讨论 B**。这两个决定以后会影响我们的视频处理流程。

可以，那就定为**完整手机号**。

水印显示格式可以设为：

> **张三 13812345678**

后台继续支持分别控制：

* **显示内容**：姓名 / 手机号 / 姓名+手机号 / 自定义文字
* **位置**：左上、右上、左下、右下、居中
* **透明度**
* **字体大小**
* **边距**
* **固定 / 缓慢随机移动**
* **移动间隔**

我建议默认：

```text
水印：张三 13812345678
透明度：30%
大小：16px
位置：随机移动
移动间隔：20秒
```

另外，**手机号只在播放时动态生成，不写进视频文件**。这样同一个视频给不同学员播放，会显示不同水印，也不需要重新编码。

这样 A、B 两项就可以定下来了。接下来重点就只剩**播放器本身的交互和手机端体验**了。

# 现在还有一个我认为必须讨论的问题

### **视频到底由谁来生成 AES-128 加密？**

有两个方案：

**方案 A：你电脑切片时直接完成 AES-128 加密。**

```text
电脑
↓
FFmpeg
↓
加密 HLS
↓
SFTP
```

优点：

> 服务器几乎不承担转码/加密压力。

**方案 B：你电脑只切普通 HLS，上传后服务器自动加密。**

```text
电脑
↓
普通 HLS
↓
SFTP
↓
服务器加密
↓
正式视频
```

优点：

> 你电脑端流程最简单。

考虑到你已经准备自己用 FFmpeg 做 HLS，我个人更倾向：

> **A：电脑端直接生成 AES-128 加密 HLS。**

服务器只负责：

> **存储 + 鉴权 + 播放。**

这样对你这台 **200Mbps 的阿里云轻量服务器**压力最低。
对，**确定采用电脑端完成 AES-128 加密 HLS**。

这样整个视频生产链就定下来了：

```text
原始录课视频
      ↓
电脑 FFmpeg
      ↓
HLS 切片
      ↓
AES-128 加密
      ↓
SFTP 上传
      ↓
服务器 /video-inbox/
      ↓
后台扫描
      ↓
自动匹配课程/课时
      ↓
正式发布
```

### 电脑端最终生成的结构

例如大培优第86页：

```text
086/
├── index.m3u8
├── key.key
├── 000.ts
├── 001.ts
├── 002.ts
├── 003.ts
└── ...
```

不过这里有一个关键点：

**`key.key` 不能直接以公开文件的方式放到服务器上。**

上传以后，系统会把它纳入受保护的视频体系：

```text
播放器
 ↓
请求 M3U8
 ↓
服务器返回经过处理的播放地址
 ↓
播放器请求 Key
 ↓
验证 Token + 用户权限
 ↓
返回 Key
 ↓
解密播放
```

所以即使别人拿到了：

```text
index.m3u8
```

也不能直接拿走 `key.key` 播放。

## 还有一个安全细节需要定

AES-128 的 Key **不能所有视频共用一个**。

我建议：

例如：

这样也符合你之前提出的：

接下来我建议讨论最后一个比较大的技术问题：

**“服务器到底采用 Nginx 直接做 HLS 鉴权，还是 WordPress/PHP 做鉴权后再交给 Nginx 传视频？”**

这个决定会直接影响你那台 **200Mbps 阿里云轻量服务器**的负载和并发能力。
**选 Nginx 鉴权，WordPress 只负责“决定有没有权限”。**

这是更适合你这个项目的方案，尤其是你用阿里云轻量服务器、200Mbps 带宽。

### 最终架构

```text id="y7n8q3"
学生点击播放
      ↓
WordPress
验证：
登录状态
+
课程授权
+
试看权限
      ↓
生成短时 Token
      ↓
Nginx
验证 Token
      ↓
M3U8 / Key / 视频分片
      ↓
直接传给学生
```

### 为什么不让 PHP 直接传视频？

如果：

```text id="6w9p2m"
学生
 ↓
WordPress/PHP
 ↓
视频
```

所有视频流量都经过 PHP，服务器负载会明显增加。

而 Nginx 非常适合干这个：

> **大量、持续的视频文件传输。**

WordPress/PHP只处理：

> **“这个人有没有资格看？”**

验证完就退出数据传输链路。

---

## Nginx 再负责三件事

### ① 防盗链

没有合法 Token：

> **403**

### ② Token 有效期

例如：

> 20分钟。

过期以后：

> 重新申请。

### ③ 禁止直接访问视频目录

即使有人知道：

```text id="k2q7v9"
/video-protected/xxxx/index.m3u8
```

直接访问：

> **403**

必须经过合法播放请求。

```text id="k3x6n1"
 ↓

 ↓
有权限？
 ↓
返回AES Key
```

所以：

**M3U8、Key、TS/分片全部不能裸奔。**
