## 2026-08-30 · 进度文档分卷机制

本项目原先只有一个持续增长的 `网站开发进度.md`。由于单文件可能过大，且 API/AI 读取容易发生截断，建立新的分卷机制：

```text
wp/wp-content/
├── 网站开发备忘录.md
├── 网站开发接班提示词.md
└── 网站开发进度/
    ├── README.md
    ├── 00-项目状态.md
    └── 01-开发记录.md
```

规则：

- `00-项目状态.md` 只保存当前状态，不累计历史。
- `01-开发记录.md` 开始保存详细历史。
- 单卷约 20～30 KB 后自动建立下一卷。
- `README.md` 负责索引和说明读取顺序。
- 不删除旧卷、不用不完整内容覆盖历史。

迁移的目的不是丢弃历史，而是让未来 AI 可以快速读取“当前状态 + 最新一卷”，需要追溯时再读取旧卷。

`wp/wp-content/plugins/math-course/includes/Tutor/class-complete.php`

课时完成规则必须只有一个来源，避免 Player、Legacy AJAX、Progress AJAX 各自形成不同的完成逻辑。这样可以保证 Lesson → Course 验证、Access 权限和完成状态统一由 Progress Service 管理。

### 当前状态

## 2026-08-30 · 旧版课时完成入口进一步统一

### Commit

`1ed10b366713aea7b72451e16bb992569100c4a4`

### 修改文件

`wp/wp-content/plugins/math-course/includes/Tutor/class-complete.php`

### 本次检查发现

全项目扫描课时完成入口时发现 `Tutor\\Complete` 仍保留一个旧的 `mathcourse_complete` AJAX action。旧实现直接把客户端传入的 `course_id`、`lesson_id` 写入 `mathcourse_learning`，这会形成第二套完成记录路径，并可能绕过 Progress Service 的 Lesson → Course 与 Access 规则。

### 已处理

兼容入口现在仅保留 AJAX action 本身，完成请求统一转交 `Progress_Service::complete_lesson()`：

- nonce 必须有效；
- 必须登录；
- 只接受并验证 `lesson_id`；
- `course_id` 不再作为可信参数；
- 不再直接调用旧 `Complete_Service` 写表；
- Progress Service 负责课程归属、课程/课时状态和观看权限；
- 完成失败时返回明确的 AJAX error，而不是无条件 success。

### 为什么这样做

课时完成必须只有一个业务入口。这样 Player、旧版 AJAX 和新的 Progress AJAX 最终都遵守同一套规则，避免“页面显示已完成，但另一套表没有记录”或“未授权用户可以伪造 course_id 完成课程”等问题。

### 当前状态

代码层面的旧完成入口已收口。仍需要继续搜索 `mathcourse_learning`、`Complete_Service`、`complete_lesson` 以及其他 AJAX/REST action，确认不存在其他独立写入路径。

### 测试与风险

本次为代码层安全修复，尚未连接真实 WordPress/Tutor 环境执行请求测试。后续需要验证登录、nonce、已授权、未授权、试看和重复完成等实际响应。

## 2026-08-30 · Access 播放权限增加发布状态防护

### Commit

`00d2b2d8d1402933145e861c8edee685ed0ef468`

### 修改文件

`wp/wp-content/plugins/math-course/includes/Access/class-access-service.php`

### 本次完成

继续检查 Progress / Player / HLS 权限链时发现，`can_preview()` 原本只验证 Lesson 属于目标 Course 以及 Lesson 是否标记为 Preview，没有显式要求 Course 和 Lesson 都是已发布状态。

虽然 Video Router 自身已有 Lesson → Course 的发布状态检查，但权限层本身也应该保持完整，避免其他业务调用 Access Service 时得到错误的播放权限结果。

现在 `can_preview()` 和 `can_watch_lesson()` 都会先验证：

1. Tutor Adapter 可用；
2. Course 存在且 `post_status=publish`；
3. Lesson 存在且 `post_status=publish`；
4. Lesson 实际归属于传入的 Course；
5. 未授权用户最终仍只能通过明确的 Preview 属性获得试看权限。

### 设计原因

Access Service 是最终观看权限来源。发布状态和 Lesson → Course 关系应该在这一层直接成立，而不是依赖调用方额外保证。这样可以降低草稿、错误 Lesson ID 或跨课程 Preview 属性造成权限绕过的风险。

### 当前状态

代码层面的课程/课时发布状态防护已经加入。真实 WordPress + Tutor LMS 环境仍需要测试草稿、私有、已发布和授权撤销等实际行为。

### 下一步

继续全项目扫描 Tutor API、Access Service、HLS URL 输出和 Progress/Player 完成接口，并确认没有其他入口绕过统一权限链。
