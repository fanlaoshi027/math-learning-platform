`Tutor Adapter → Course Service → Access / Progress / Video → 前台`

## 2026-08-30 · 进度文档分卷机制

本项目原先只有一个持续增长的 `网站开发进度.md`。由于单文件可能过大，且 API/AI 读取容易发生截断，建立新的分卷机制：

```text
wp/wp-content/
├── 网站开发备忘录.md
├── 网站开发接班提示词.md
└── 网站开发进度/
    ├── README.md
    ├── 00-项目状态.md
    └── 01-开发记录.md
```

规则：

- `00-项目状态.md` 只保存当前状态，不累计历史。
- `01-开发记录.md` 开始保存详细历史。
- 单卷约 20～30 KB 后自动建立下一卷。
- `README.md` 负责索引和说明读取顺序。
- 不删除旧卷、不用不完整内容覆盖历史。

迁移的目的不是丢弃历史，而是让未来 AI 可以快速读取“当前状态 + 最新一卷”，需要追溯时再读取旧卷。

## 2026-08-30 · HLS URL 生成层防御性权限校验

### Commit

`06d466ca1ac14907c5b4ca516a38e6fa02f687cf`

### 修改文件

`wp/wp-content/plugins/math-course/includes/Video/class-video-router.php`

### 本次完成

1. `Video_Router::get_protected_url()` 增加最终 `can_watch()` 校验。
2. URL 生成不再只检查 Lesson 是否存在，而是同时检查当前用户是否拥有课程观看权限，或该课时是否允许游客试看。
3. 保留 `handle()` 请求阶段的二次权限校验。
4. 形成“生成 URL 前一次授权 + 实际请求时再次授权”的纵深防御。

### 修改原因

之前 Course Service 在生成播放数据时已经调用 Access Service，但 `Video_Router::get_protected_url()` 本身没有授权判断。未来其他业务代码如果直接调用该方法，可能绕过上层调用者的权限检查而获得受保护 URL。虽然实际 HLS 请求仍有权限验证，但 URL 生成层本身也应该是授权边界。

### 当前状态

视频播放权限现在至少经过两个边界：

`Course/调用方 → Access → get_protected_url()`

以及：

`受保护 URL → Video_Router::handle() → Access → 源站`

### 测试/风险

本次为静态代码级修复，尚未连接真实课程和真实 HLS 源进行端到端测试。游客试看、已授权用户、未授权用户、管理员仍需要真实环境分别验证。

### 下一步

继续检查 URL 编码、HLS 子资源路径和 Progress/Player 调用链，并进行全项目 Tutor API / Access Service 绕过扫描。

## 2026-08-30 · HLS URL 生成层二次检查

### Commit

`06d466ca1ac14907c5b4ca516a38e6fa02f687cf`

### 修改文件

`wp/wp-content/plugins/math-course/includes/Video/class-video-router.php`

### 本次完成

在继续检查 HLS 网关时确认并保留了 URL 生成层的纵深权限设计：`get_protected_url()` 不仅检查 Lesson 存在，还调用 `can_watch()`；实际请求进入 `handle()` 后再次检查权限。这样即使未来有其他业务调用 Video Router，也不能单靠 Lesson ID 直接取得受保护播放地址。

### 代码级验证

- 当前用户登录并拥有课程权限：允许生成保护 URL。
- 游客且课时明确允许试看：允许生成保护 URL。
- 未授权且非试看：返回空地址。
- 已取得旧 URL 后，实际网关请求仍会再次检查权限，因此权限撤销后旧 URL 不应继续获得源站内容。

### 尚未完成

以上仍属于静态代码检查，真实服务器、真实 HLS 文件、iPhone Safari 和完整 m3u8 仍需实测。
